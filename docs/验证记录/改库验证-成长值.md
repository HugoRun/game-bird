# 改库验证记录：捕捉结算页成长值

本文件记录一次**真实写库 → 观测 → 复原**的完整验证过程，用于证明结算页展示的成长值
来自真实落库数据，而非模板捏造。

>执行环境：`docker compose` 起的 MySQL 8.0 + Spring Boot 3.2.7 容器。
>凭据从 `docker/.env` 注入环境变量，命令行零明文口令。

---

## 验证目标

证明 `GET /trap/over` 结算页展示的「成长」百分比，直接来源于本次捕捉写入
`storage_bird.grow` 的真实值，而不是模板里写死的数字。

---

## 前置：架构师规格本身的缺陷（重要）

原验证规格是：

> 捕捉一只鸟 → 记录 grow → `UPDATE storage_bird SET grow=250` → **重开结算页**
> → 必须显示 `2.50%`

**这一步物理上不可执行。** 已实测确认（并由 team-lead 独立复核 `TrapController.java:230-262`）：

| 事实 | 位置 | 后果 |
|---|---|---|
| `role_trap` 的 `catch_*` 字段在收网后被**全部清零** | `TrapController.java:230-237` | 没有"待结算"的中间态可供重开 |
| 页面展示的 `bird` 是**本次捕捉流程的内存对象**（由 `useBait` 随机生成、经 `insertStorageBird` 落库） | `TrapController.java:256-257` | 页面**不回读** `storage_bird` |
| `/trap/birdInfo` 只读 `base_bird` 配置 | `TrapController` | 该页只有类型/重量/单价/经验，**无成长值** |

结论：这是**验证规格的缺陷，不是数据流缺陷**。结算页是**一次性渲染**，无按 birdId 重开入口。
已就此上报，team-lead 裁决采纳方向 A（零代码改动），不授权新增重开入口（属新增功能，与本轮红线冲突）。

---

## 实际执行的验证

### 步骤 1：捕捉（写库）

```
POST /trap/useBait?baitId=34&trapId=15      -> 302 Location: /game
```

`role_trap` 落库状态：

```
bait_id=34  catch_bird_id=1  catch_end_time=2026-10-14 23:45:34
```

### 步骤 2：结算（等`catch_min=2` 分钟到期后）

```
GET /trap/over?trapId=15                    -> 200
```

页面实际文案：

```
成长:10.00%    克制:0.00%
```

落库记录：

```
SELECT id, bird_id, grow, ko FROM storage_bird WHERE id=101;
  id=101  bird_id=1  grow=1000  ko=0
```

**`1000 / 100 = 10.00%`，页面与库值严格一致 → 排除捏造值。**

> `baitId` 必须是 `role_pack.id`（34）而非 `base_bird.base_id`（1）——
> `trapService.getById(baitId)` 查的是 `role_pack` 主键。传错会得到「诱饵数量不足」。

### 步骤 3：改库

```sql
SELECT id, bird_id, grow, ko FROM storage_bird WHERE id=101;  -- 101  1  1000  0
UPDATE storage_bird SET grow = 250 WHERE id = 101;
SELECT id, grow, ko FROM storage_bird WHERE id = 101;        -- 101  250  0   ✅ 已改
```

尝试观测：

```
GET /trap/birdInfo?birdId=101    -> 200，但页面无成长值（无重开结算页的入口）
```

### 步骤 4：复原（已执行）

```sql
UPDATE storage_bird SET grow = 1000 WHERE id = 101;
SELECT id, bird_id, grow, ko FROM storage_bird WHERE id = 101;  -- 101  1  1000  0   ✅ 已复原
```

**数据库已回到验证前状态，无残留。**

## 等效证明链

原规格的第4 步无法执行，改由以下三点共同构成完整证明：

| # | 证据 | 说明 |
|---|---|---|
| 1 | 步骤 2 的页面文案与库值严格对应 | `10.00%` ↔ `grow=1000`，已排除模板捏造 |
| 2 | `BirdTextUtilsTest:19-20` 锁死换算契约 | `growText((short)1000) == "10.00%"`、`growText((short)250) == "2.50%"` |
| 3 | 步骤 3 的UPDATE 确实生效（读回 250） | 证明写库链路通畅，值本身可变；缺的只是"重开页面"这个观测手段 |

即：**换算逻辑由单测锁死、落库数据由实测对应、写库链路由步骤 3 证明**，
三者合起来覆盖了原规格想验证的全部内容。

## 顺带纠正的规格错误（架构师 SQL 与实际库结构不符）

| 规格里的 SQL | 实际报错 | 实际列名 |
|---|---|---|
| `SELECT id, name, grow, ko FROM storage_bird` | `ERROR 1054 Unknown column 'name'` | `bird_id`（`storage_bird` 无 `name` 列） |
| `SELECT role_id, name FROM role` | `ERROR 1054` | `role_name` |
| `SELECT p.kind, p.base_id FROM role_pack` | `ERROR 1054` | `type_id` |
| `SELECT id, name, price, type FROM base_trap` | `ERROR 1054` | `fee_price`、`fee_type` |
| `SELECT id FROM account ORDER BY id DESC` | `ERROR 1054` | 主键是 `user_id` |

**结论：规格里的 SQL 也必须验证，不能照抄。** 建议后续规格文档附`SHOW COLUMNS` 输出。
